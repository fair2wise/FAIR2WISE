# T19E operations integration evidence (for H6)

- **Gate:** H6 ("T19E operation access"). **Scope here:** agent, API, SDK and CLI closure of the five T19C Knowledge Operations (plus the T19B paper summary, already closed at H2). The frontend part of T19E and anything that depends on T15 (FORGE consumer) are not part of this record.
- **Branch:** `forge_merge-T19E-ops-wiring` on `forge_merge` `d99f4e9`. Not merged.
- **One implementation.** Every surface calls the T19C suites (`app/modules/operations/{graph,corpus}.py`) through one bundle, `app.modules.operations.knowledge.KnowledgeOperations`. No surface adds a metric, a population rule or a model call; the T19C contract holds on each: read-only, `chat.ask`, bounded output (`reports.fit_report`), `partial` never reported as `ok`, D19 guard inside every report (`check_no_source_material`), and the T19C scope rule (a graph or corpus outside a non-empty `corpus_scope` is `DENIED`).
- **Legacy scripts.** `scripts/analyze_kgs.py` and `scripts/corpus_qa.py` are byte-identical to the T19A baseline (`tests/operations/test_graph_operations.py::test_legacy_block_matches_analyze_kgs_on_committed_graphs`, `tests/operations/test_corpus_audit.py::test_cli_is_unchanged`). They remain the parity oracle; the CLI wrappers of the "one implementation with CLI wrappers" acceptance are the `python -m app.api.cli ops ...` subcommands (`docs/migration/operations_inventory.md` section 10).

## 3. Design notes and limits

- **Routes.** `/v1/operations/{statistics,compare,paper-subgraph,recent,corpus-audit}` (GET, `chat.ask`), `POST /v1/operations/jobs` (`ops.run`, fresh role check) and `GET /v1/operations/jobs/{job_id}` (job visibility). Handlers are thin over `F2WOperations.{graph_statistics,compare_graphs,paper_subgraph,recent_entities,audit_corpus,submit_knowledge_operation,knowledge_job_result}`.
- **Default wiring.** `create_api_app` builds `KnowledgeOperations.from_storage(Path.cwd())` (JSON graphs under `storage/kg`, corpora under `storage/terminology`, as the legacy UI lists them) unless the caller passes `knowledge_operations=` or `operations` already carry one, and registers the `knowledge_operation` kind with `knowledge_job_context` (local operator on `:local`; on ALS the initiating subject's current credential through the job authority's lookup). A Tiled-backed deployment passes a `KnowledgeOperations` over `TiledGraphBackend` (as GKT does); no default Tiled port is built from settings here.
- **Job scope.** A job's `corpus_scope` defaults to the graph ids / corpus its arguments name (`knowledge.job_scope`), so `JobService` applies the same scope rule the inline read applies.
- **CLI.** `ops ...` subcommands build JSON ports only (`--project-root`, `--graph-file`); `ops submit` registers the job kind on the CLI's own store so the same-root worker can run it; `ops result <id>` reads the bounded report back. Tiled graphs reach the CLI through the API or the SDK, not through a CLI port.
- **Not done here.** Frontend surfacing of operation results in the legacy UI chat (the UI QA turn keeps its verdict contract; see the T03B note above) and any FORGE-consumer path (T15). Owner items are listed in the T19E report.
