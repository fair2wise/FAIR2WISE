2. Scope and ownership: the non-negotiable boundary
2.1 F2W owns
- Literature discovery, bibliographic resolution, PDF intake, parsing, corpus manifests, citations and source assets.
- Literature-focused agent supervision, task skills, tool contracts, durable ingestion jobs and reviewable publication.
- Schema-guided extraction, paper-reported scientific records, term identity, vocabulary governance, evidence grounding and uncertainty resolution.
- Literature KG construction, repair, versioning, querying, retrieval, grounded answers and provenance of those operations.
- Paper figures, panels, tables, q-axis/scale readings and source-supported orientation statements. These are document-reading capabilities, not experimental image analysis.
- Preservation of existing F2W paper-related behavior, including code snippets and their source/license provenance where present. Extracting code from literature does not authorize executing it.
2.2 FORGE continues to own
Experimental dataset discovery and inspection; raw-frame reduction; detector calibration; peak indexing; simulation; fitting; beam optics; training estimators; experimental image/model inference; acquisition and live-run workflows. The migration does not introduce RunCard, new FORGE experimental-run discovery/control, or FORGE's analysis/simulation dependencies into F2W. The inspected F2W branch already has live Tiled lookup, ops-document retrieval and Materials Project evidence paths; preserve these existing UI/QA behaviors through adapters. Removing or transferring existing behavior is a separate owner decision, not an automatic consequence of the donor-port scope.
A Tiled Graph literature adapter is mandatory for the first release, supporting both application-managed and central-server deployments (D13-D15). This does not bring experimental Tiled-run ownership into F2W. Versioned JSON is the KG creation artifact, not merely a cache or export of Tiled. Validated JSON snapshots can be used locally and ingested into Tiled Graph through the required publication adapter. Splash is not a supported target service. The supplied browser snapshot nevertheless sends graph_source="splash" and stores graphSource="splash_links"; preserve that legacy wire vocabulary via an explicitly configured Tiled compatibility adapter. Legacy tokens are not permission to run Splash or reuse unverified old credentials. See section 5.2 and FRONTEND_COMPATIBILITY.md. A paper may describe simulation/analysis; F2W records its evidence while FORGE executes the computation.
2.3 Ownership at the integration boundary
FORGE may call F2W to search papers, obtain evidence, retrieve literature context, request an ingestion job, or ask a literature question. F2W decides whether literature records pass validation and whether an authorized publication may occur. FORGE may use the returned evidence in its own simulation recipe, but may not relabel simulated outputs as literature observations or overwrite F2W-owned evidence.
Keep relate_sample_to_literature in FORGE because it combines sample context and simulation preparation. Refactor its literature lookup to F2W; retain sim_build_recipe_from_paper and simulation feasibility/mapping in FORGE. Preserve evidence IDs and source citations across the call.
2.4 Explicit non-goals
No new shared mega-agent, no src-layout relocation, no new Splash backend, no mandatory MCP server, no full frontend rewrite, no automatic ontology union, no replacement of F2W's LLM classes or QA policy, no replacement of the extractor before evaluation, no default full-corpus re-extraction, no global graph wipe, and no unapproved paid-model or external reviewer workflow. Broad capability counts from earlier slides are not acceptance criteria.

4.2 Two execution modes, one service layer
Interactive literature QA: preserve the exact branch's request handling, retrieval, evidence hydration, context construction, answer constraints, citations, abstention/fallback and enrichment approval behavior. The migration adds no new right to ingest/publish when retrieval is weak. Preserve any existing authorized enrichment flow as a separate policy-controlled job. Do not replace the F2W QA system prompt with FORGE's supervisor/science prompts; archive the baseline and test compatibility.
Background literature build: approved inputs -> bibliographic identity -> parser -> extraction strategy -> evidence validation -> canonicalization -> scientific record assembly -> versioned JSON KG creation -> snapshot validation/review. Separate publication: an approved JSON snapshot -> Tiled import plan -> resumable import -> verification/receipt -> publication/index activation. Each expensive stage is resumable and independently inspectable. A supervisor may choose tasks; a typed job pipeline enforces their state transitions and cannot be bypassed by prompt wording.
Evidence and operational provenance are related but different. Evidence links a claim/value to a source version and location. Execution provenance records which tool/model/prompt/code produced or transformed it. Neither a successful ToolCall nor high model confidence establishes a scientific fact.

8.2 Parallel working rules
Use forge_merge as the sole F2W integration branch and BRANCH_WORKFLOW.md as the branch authority. Parallel workers may use task-scoped scratch branches/worktrees based on forge_merge; their reviewed commits must be integrated there, never into main/rsoxs. One integrator owns the integration worktree. Do not check out forge_merge in multiple worktrees or share dirty directories. Use one isolated corpus/cache/DB root per worker. Pin contracts and update scratch branches from approved integration checkpoints without rewriting another worker's history. Do not edit the same monolith simultaneously: extract a narrow seam or assign one owner while others implement tests/adapters. Limit each PR to one behavior change or one mechanical move when practical.
Parallel parser/extractor jobs are bounded by CPU/RAM/model/server budgets, not merely the number of agents available. Enforce the effective shared provider/account rate and concurrency limit across chat, sync/async workers, evaluations and delegated calls in addition to job-local limits; do not multiply the configured quota by worker count. Parallel reads are acceptable within access scope; mutable vocabulary activation, canonical-merge apply, graph promotion and active-index switching require serialized ownership.
Reviewers may inspect independent code and gold examples in parallel. A worker cannot approve its own migration, adjudicate its own gold labels as authoritative, or let an automated reviewer impersonate a human decision. Live evaluation uses the selected F2W provider/model and approved input scope under the same admission controls as other callers. Do not introduce automatic paid escalation or broaden provider data access. Ordinary authorized use is not blocked on an invented dollar cap.

11.2 Keys, receipts and replay
An operation key includes corpus scope, source checksum, Work/source version, stage, parser/extractor version, model/prompt/schema/vocabulary revisions and relevant parameters. Do not put secrets in keys or logs. Preserve historical identity and changed-source relations rather than overwriting evidence in place.
A stage records intent, obtains an owned lease, performs effects with stable IDs, verifies outputs and writes a durable completion record. A worker may repeat a stage after a crash. Safe resumption depends on idempotency and effect reconciliation, not an unqualified exactly-once guarantee. Receipts are valid only for the target and revision they identify.
11.3 Mandatory failure-injection cases
- Crash after PDF download but before manifest update: recover or quarantine the verified asset without duplicate acquisition.
- Crash during parsing/extraction: retain successful compatible chunks; incomplete coverage blocks publication.
- Lease expiry while a worker is still alive: prevent a stale owner from applying later mutations using an ownership token/revision check.
- Crash after graph entities but before links/receipt: reconcile by stable IDs and complete the scoped plan without duplicate scientific facts.
- Crash after publication but before active index switch: old graph/index pair remains usable until a verified new pair is activated.
- Approval arrives after candidate/schema/vocabulary changed: reject as stale and request new review.
- Provider bills a failed response or omits cost header: settle/reconcile explicitly; never mark unknown cost as free.
- Read returns only a page/cap of graph results: abort deduplication/repair rather than treating unobserved entities as absent.
- Worker/telemetry process cannot write an audit event: report degraded status; block critical mutations if durable audit cannot be guaranteed.
- User scope changes or a credential is revoked: invalidate dependent access-sensitive cache and approvals; do not fall back to an unrestricted server credential.
