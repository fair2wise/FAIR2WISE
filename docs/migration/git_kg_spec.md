Git-versioned JSON KG release and staging-to-production promotion
Draft v7. D21 and D31: create versioned JSON first; commit the frozen KG; import the tested artifact. Git data version, image digest and Tiled import receipt are different identities.
1. Repository contract
Store reviewed immutable JSON KGs in the F2W repository, integrated through forge_merge during this migration. A proposed layout is:
storage/kg/<corpus>/<snapshot-id>/
    graph.json
    manifest.json
    validation.json       # sanitized result/record or approved reference
Preserve existing graph file/selection conventions via compatible references. The layout is a proposal, not permission to break current readers. No overwrite of old frozen versions. A new record set or reconciled admin edit creates a new version. Do not automatically git add, commit or push from an LLM Tool; the operator/release workflow owns review and Git writes.
The manifest binds exact graph bytes, schema/import fingerprints, extraction/corpus revisions, parent snapshot and necessary evidence/source checksums. Preserve F2W things/associations and existing IDs. Hash exact stored bytes rather than implicitly normalizing them at deployment. A release record created after Git commit binds repository, commit, path, graph/manifest hashes, staging binary report, compatible code/schema/importer and selected target. Do not put a commit's own hash inside its file content and introduce a circular identity requirement.
2. What may be committed
Commit the actual reusable KG artifact and safe manifests, not only a pointer to an untracked developer file. Preserve derived facts and the approved bounded exact evidence quotations. Full papers, reconstructed source bodies, parsed sections, original table/figure crops, API keys, cookies, credentials, local filesystem paths, private job/checkpoint/trace stores and original paper caches stay out of Git. Private evidence uses stable protected references/checksums, not publicly retrievable bearer URLs.
Before staging files, run allowlisted path, source-disclosure and secret checks. Review the repository's actual visibility; no auth at /fair2wise protects bytes already committed to a public repository. If current graph payloads contain restricted raw source, separate that private payload with explicit references, preserve scientific fields, review the projection and test the exact resulting version. Do not silently redact a validated artifact at production transfer and claim it has the old hash. Large-file storage policy, if needed, must be explicit and verify actual JSON bytes after retrieval; do not silently replace JSON with unavailable external links.
3. Promotion sequence
1. Build a candidate JSON snapshot using the preserved F2W pipeline, with sources private and schema semantics unchanged. Tiled is not required to construct it.
2. Validate scientific/data structure, field retention and disclosure. Freeze the bytes and manifest. Execute the required binary suite for this version and bind results to its hash.
3. Review and commit the selected JSON/manifest under the approved branch workflow. Confirm the committed blob exactly matches the tested bytes; any rewrite, merge conflict or manual edit produces a new hash and requires corresponding validation. Record immutable Git identity after the commit exists.
4. Validate the committed artifact on staging with the approved application/schema/importer. The staging report and import receipt identify the same bytes. A working-tree filename or mutable branch tip is not enough to select production data.
5. Create a production-specific promotion/import plan identifying the data commit, path, hashes, production target, scope and expected base revision. Require the authenticated production Tiled admin's explicit approval and the relevant project/deployment gates. A staging admin role or receipt is not production authorization.
6. A deployment/operator step exports the allowlisted files from that exact Git commit into production's mounted KG storage. Do not rerun extraction, parsing, a model, canonicalization, or a schema migration. Verify JSON/manifest hashes, required schema/importer compatibility and private evidence dependencies before activating anything.
7. Import through the existing JSON-to-Tiled adapter using the production technical writer. Reconcile resumable effects, verify readback, record a distinct production receipt and activate the version/index coherently. Source JSON stays immutable.
8. FORGE consumes the published literature using stable IDs and the selected production F2W/Tiled pair. Preserve the snapshot ID, citations and provenance across that boundary.
A validation step may read a committed artifact before or after its initial commit, but the production candidate must be provably the identical version that passed staging. If a suite includes live QA, that evaluation is separately authorized and recorded; the import/transfer operation itself never calls inference.
4. Deployment is not image bundling
Git-tracked does not mean Docker-bundled. All three images still exclude corpus JSON, papers and private state from their build context and layers. Use allowlisted COPY or an explicit sanitized context; test with a committed fixture snapshot to prove this exclusion. Ansible/operator export places the approved data on runtime mounts separately from image rollout. Do not give containers Git push credentials or require a writable checkout to serve the application.
Source papers, parsed assets and private evidence needed for production QA remain separately authorized mounted resources. Verify required references/availability on the destination; a JSON import does not transfer those files or license access to them. Missing required assets produce a clear blocked/degraded state, not hidden re-extraction. Git covers committed KG versions; it is not a backup for private source assets, operational audit or Tiled itself.
5. Admin edits and rollback
Approved admin edits may be reflected immediately through the existing UI contract where supported, with stable identity, explicit base revision and a durable edit journal. Reconcile them into a new JSON version, validate, commit and promote that version before claiming they are part of the cross-environment release. Re-importing an older file must not erase an acknowledged newer edit. Conflicts require explicit handling, not last-writer-wins by accident.
Rollback selects a previous approved commit/path/hash and creates a target-specific reviewed reactivation/import plan. It does not rewrite Git history or delete later candidate/audit records. Code rollback and graph rollback are independently chosen based on compatibility. Import receipts are private operational state; sanitized status may reference them without committing live credentials/approval tokens.
6. Proposed implementation seams and parallel work
- app/modules/graph/releases.py: validate_commit_candidate, verify_snapshot_selection, verify_release_dependencies, export_snapshot_selection. Names are proposed, not donor symbols.
- app/modules/graph/snapshot_manifest.py: reused immutable payload/manifest identity.
- app/modules/graph/imports/tiled_json.py and receipts.py: existing planned importer with Git/data-release identity, no inference.
- scripts/prepare_kg_release.py: operator facade for validation/export; no auto-push.
- .github/workflows/: fixture/secret/disclosure/committed-hash checks; no inference or central import on an ordinary push.
- Ansible deployment handoff: data_repository/data_commit/data_paths/data_hashes and read-only fetch/export credentials, independently of image_ref.
T26A freezes contract at H1; T26B implements commit-ready checks and disposable Git fixtures before H4; T26C demonstrates staging-to-second-target promotion/rollback for H5/H6. Parallel domain ports produce scientific records without implementing their own Git publishing code.
Binary cases must cover committed equals tested bytes, altered blob rejection, no production re-extraction, separate target receipts/authorization, source-disclosure scanning, tracked JSON excluded from images, missing private evidence, stale approval/role, Git-versus-image version independence and edited-version reconciliation. These are test requirements, not results.
