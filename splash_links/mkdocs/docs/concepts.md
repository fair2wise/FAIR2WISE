# Concepts and storage

## Graph records

Splash Links stores three public record types:

| Record | Required data | Optional data |
|---|---|---|
| Entity | UUID, entity type, name, creation time | URI and JSON properties |
| Link | UUID, subject UUID, predicate, object UUID, creation time | JSON properties |
| Embedding | UUID, owner entity, model label, normalized vector, dimensions, creation time | JSON properties |

A link is directional: `(subject) -[predicate]-> (object)`. The store verifies
that both endpoint entities exist before creating a link. Entity UUIDs and link
UUIDs are generated by Splash.

`uri` is the stable external identifier slot. Applications can preserve their
own identifiers there and retain additional source fields in `properties`.
FAIR2WISE imports a MatKG node ID into both `uri` and the `matkg_id` property.

## Updates and deletion

Entity updates can change `name`, `uri`, and `entity_type`. Supplied properties
are merged into the existing property object. Link updates change the
predicate.

Deleting an entity cascades to links and embeddings attached to it. Deleting a
link or embedding does not delete either endpoint entity.

## Pagination and ordering

Entity, link, and embedding list operations accept `limit` and `offset`.
GraphQL defaults to 100 records. REST embedding lists enforce a limit from 1
through 1000. Clients loading a complete graph must paginate until a page is
shorter than the requested page size.

## Embeddings

Vectors are normalized before storage. Empty vectors and zero-magnitude
vectors are rejected. Searches compare vectors of matching dimension and
return cosine distance, where lower values are nearer.

SQLite stores packed vector data and performs cosine ranking in Python.
PostgreSQL uses `pgvector` storage and database-side ordering when the extension
is available.

## Database selection

`SPLASH_LINKS_DB` accepts either a plain SQLite path or a SQLAlchemy URL:

```text
links.sqlite
/data/links.sqlite
:memory:
sqlite:///links.sqlite
postgresql+psycopg2://user:password@host/splash_links
```

| Backend | Recommended use | Notes |
|---|---|---|
| SQLite file | Local and single-user deployments | Portable single-file database |
| SQLite memory | Unit tests and disposable processes | Data disappears at shutdown |
| PostgreSQL | Concurrent or multi-user deployments | Supports native vector search |
| DuckDB | Experimental evaluation | Not covered as a production backend |

SQLite foreign keys are enabled for every connection. PostgreSQL connections
register the vector type when `pgvector` support is installed.

## Migrations

The FastAPI lifespan converts `SPLASH_LINKS_DB` to a database URL and applies
Alembic migrations before accepting requests. In-memory databases skip
Alembic and create their schema directly.

An existing pre-Alembic database containing graph tables is stamped before the
upgrade. Back up persistent databases before deploying migrations and do not
run two migration processes against the same SQLite file concurrently.

## Service layers

Requests flow through these layers:

1. Python, CLI, and direct GraphQL callers connect to FastAPI.
2. FastAPI routes graph operations to Strawberry GraphQL and embedding REST
   operations to the embedding handlers.
3. Both interfaces use the shared SQLAlchemy store.
4. SQLAlchemy persists records in SQLite or PostgreSQL/`pgvector`.
